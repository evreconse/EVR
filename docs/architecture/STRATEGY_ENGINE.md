# EVRECONSE Strategy Engine Specification

**Document Version:** 1.0
**Status:** Draft
**Date:** 2026-07-25

---

## 1. Назначение Strategy Engine

Strategy Engine — центральный модуль системы, управляющий всеми торговыми стратегиями.

Он заменяет модуль Pattern Detector из исходной архитектуры (SYSTEM_ARCHITECTURE.md) и реализует принцип **Evolution Without Rewrite** (CORE_SPECIFICATION.md): добавление новых стратегий не требует изменения ядра системы.

Strategy Engine является единственным модулем, который:
- получает рыночные данные от Data Provider для всех отслеживаемых инструментов;
- знает о всех зарегистрированных стратегиях;
- создаёт Market Event для каждой закрытой свечи;
- делегирует проверку условий каждой активной стратегии;
- создаёт Qualified Event для каждой стратегии, подтвердившей паттерн;
- передаёт Qualified Events в Scoring Engine.

## 2. Ответственность Strategy Engine

### 2.1 Управление реестром стратегий

- Загрузка списка активных стратегий из конфигурации при старте.
- Регистрация каждой стратегии с её уникальным идентификатором (Strategy ID).
- Инициализация стратегий с их конфигурационными параметрами.
- Поддержка hot-reload для включения/отключения стратегий без перезапуска.

### 2.2 Обработка рыночных данных

- Получение закрытых свечей M15 и данных о ликвидациях от Data Provider.
- Определение момента закрытия свечи для каждого инструмента.
- Создание Market Event для каждой закрытой свечи (даже если ни одна стратегия не сработала).
- Передача данных свечи всем активным стратегиям.

### 2.3 Делегирование проверки условий

- Передача данных свечи каждой активной стратегии.
- Ожидание результата от стратегии (подтверждено / не подтверждено).
- Сбор метрик паттерна от стратегий, подтвердивших паттерн.

### 2.4 Управление жизненным циклом событий

- Создание Market Event (статус NEW) для каждой закрытой свечи.
- Перевод события в статус QUALIFIED при подтверждении хотя бы одной стратегией.
- Создание отдельного Qualified Event для каждой подтвердившей стратегии.
- Передача Qualified Events в Scoring Engine.
- Передача всех Market Events в Storage Service.

### 2.5 Изоляция стратегий

- Стратегии не имеют доступа друг к другу.
- Стратегии не знают о Scoring Engine, Notification Service, Storage Service.
- Стратегии не управляют состоянием событий.

## 3. Жизненный цикл стратегии

```
┌─────────────────┐
│   Регистрация   │  ← При старте / hot-reload конфигурации
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   Инициализация │  ← Получение параметров из Configuration Manager
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   Активное      │  ← Ожидание данных от Data Provider
│   ожидание      │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   Обработка     │  ← Получение данных свечи
│   свечи         │
└────────┬────────┘
         │
    ┌────┴────┐
    ▼         ▼
Подтверждено  Не подтверждено
    │             │
    ▼             ▼
Возврат       Возврат
метрик        «нет паттерна»
    │
    ▼
┌─────────────────┐
│   Завершение    │  ← При отключении в конфигурации / остановке системы
│   (Cleanup)     │
└─────────────────┘
```

### Состояния стратегии

| Состояние | Описание |
|-----------|----------|
| **REGISTERED** | Зарегистрирована в Strategy Engine, параметры загружены. |
| **ACTIVE** | Готова к обработке данных, получает свечи. |
| **PROCESSING** | В данный момент проверяет условия для свечи. |
| **DISABLED** | Отключена через конфигурацию, не получает данные. |
| **ERROR** | Произошла ошибка при обработке, ожидает восстановления. |
| **UNREGISTERED** | Удалена из реестра (при hot-reload или остановке). |

## 4. Правила регистрации новых стратегий

### 4.1 Требования к регистрации

1. **Уникальный Strategy ID** — строковый идентификатор (например, LW-001, LW-002).
2. **Конфигурация** — блок параметров в разделе `strategy.<ID>` (CONFIGURATION_SYSTEM.md).
3. **Реализация интерфейса стратегии** — соответствие требованиям раздела 5.
4. **Изоляция** — стратегия не должна иметь прямых зависимостей от других стратегий или модулей ядра.

### 4.2 Процесс регистрации

1. При старте Strategy Engine читает `strategy.active` из конфигурации.
2. Для каждого ID в списке загружается блок `strategy.<ID>`.
3. Проверяется наличие обязательных параметров.
4. Стратегия инициализируется и переводится в состояние ACTIVE.
3. При изменении конфигурации (hot-reload):
   - Новые ID добавляются → регистрация и активация.
   - Удалённые ID → перевод в UNREGISTERED, очистка ресурсов.
   - Флаг `enabled: false` → перевод в DISABLED.

### 4.3 Версионирование стратегий

- Каждая стратегия имеет поле `version` в конфигурации.
- Strategy Engine проверяет совместимость версии стратегии с версией ядра.
- Несовместимые версии не регистрируются (ошибка конфигурации).

## 5. Требования к интерфейсу стратегии

Каждая стратегия должна реализовывать следующий контракт (концептуальный, без привязки к языку):

### 5.1 Метод инициализации

```
initialize(config: StrategyConfig) -> Result
```

- Принимает конфигурационный блок стратегии.
- Валидирует параметры.
- Возвращает успех или ошибку конфигурации.
- Вызывается один раз при регистрации.

### 5.2 Метод обработки свечи

```
process(candle: CandleData, liquidation: LiquidationData) -> StrategyResult
```

- Принимает данные закрытой свечи и данные о ликвидациях.
- Возвращает результат проверки.

**CandleData** содержит:
- Symbol, Exchange, Timeframe
- Event Time (UTC)
- Open, High, Low, Close, Volume

**LiquidationData** содержит:
- Liquidation Volume
- Liquidation Reference Value (среднее за N свечей)

**StrategyResult** содержит:
- confirmed: Boolean — найден ли паттерн
- metrics: Object — метрики паттерна (если confirmed = true)
  - lower_wick, body, wick_body_ratio, lower_wick_pct, body_pct
  - liquidation_volume, liquidation_reference_value
- strategy_id: String — идентификатор стратегии

### 5.3 Метод очистки

```
cleanup() -> void
```

- Вызывается при отключении стратегии или остановке системы.
- Освобождает ресурсы, сохраняет состояние если необходимо.

## 8. Взаимодействие с другими модулями

### 8.1 Data Provider → Strategy Engine

**Направление:** Входящий поток

- Data Provider передаёт закрытые свечи M15 и данные о ликвидациях.
- Strategy Engine получает данные для каждого инструмента по мере закрытия свечи.
- Data Provider не создаёт события — только доставляет сырые данные.

### 8.2 Strategy Engine → Scoring Engine

**Направление:** Исходящий поток

- Strategy Engine создаёт Qualified Event для каждой стратегии, подтвердившей паттерн.
- Qualified Event содержит: все данные Market Event + Strategy ID + метрики стратегии.
- Передача происходит последовательно: один Qualified Event — один вызов Scoring Engine.
- Если несколько стратегий подтвердили одну свечу — создаются несколько Qualified Events.

### 8.3 Strategy Engine → Storage Service

**Направление:** Исходящий поток

- Strategy Engine передаёт **все** Market Events (статус NEW) в Storage Service.
- Передача асинхронная, не блокирует обработку.
- Storage Service сохраняет события независимо от результата проверки стратегиями.

### 8.4 Strategy Engine → Configuration Manager

**Направление:** Запрос конфигурации

- При старте: получение списка активных стратегий и их параметров.
- При hot-reload: получение обновлённой конфигурации.
- Strategy Engine не читает файлы конфигурации напрямую.

### 8.5 Strategy Engine ↔ Notification Service / Outcome Tracker

**Прямого взаимодействия нет.**

- Notification Service получает Scored Event от Scoring Engine.
- Outcome Tracker получает Signal от Notification Service.
- Strategy Engine не знает о существовании этих модулей.

## 9. Обработка ошибок внутри стратегии

### 9.1 Ошибки валидации входных данных

| Ситуация | Действие Strategy Engine |
|----------|---------------------------|
| Неполные данные свечи | Отбросить свечу, залогировать, стратегия не вызывается |
| Некорректные значения OHLC | Отбросить свечу, залогировать |
| Отсутствуют данные ликвидаций | Передать стратегии с пустыми/нулевыми значениями ликвидаций |

### 9.2 Ошибки внутри стратегии

| Ситуация | Действие Strategy Engine |
|----------|---------------------------|
| Стратегия вернула ошибку | Залогировать, перевести стратегию в ERROR, продолжить с другими стратегиями |
| Стратегия не ответила за таймаут | Прервать вызов, залогировать таймаут, перевести в ERROR |
| Стратегия вернула некорректный результат | Залогировать, игнорировать результат этой стратегии |

### 9.3 Принципы устойчивости

- Ошибка в одной стратегии **не должна** останавливать обработку другими стратегиями.
- Ошибка в стратегии **не должна** блокировать создание Market Event.
- Strategy Engine должен изолировать исключения/ошибки отдельных стратегий.
- После ошибки стратегия может быть автоматически восстановлена при следующем вызове или требовать ручного сброса (настраивается).

## 10. Включение/отключение стратегий через конфигурацию

### 10.1 Конфигурационные параметры

Согласно CONFIGURATION_SYSTEM.md:

| Параметр | Тип | Описание |
|----------|-----|----------|
| strategy.active | Array | Список ID активных стратегий |
| strategy.<ID>.enabled | Boolean | Флаг активности конкретной стратегии |
| strategy.<ID>.condition.* | Number | Параметры условий |
| strategy.<ID>.risk.* | Number | Риск-параметры |

### 10.2 Hot-reload поведение

| Действие | Поведение Strategy Engine |
|----------|---------------------------|
| Добавлен новый ID в strategy.active | Регистрация и активация новой стратегии |
| Удалён ID из strategy.active | Graceful shutdown стратегии, перевод в UNREGISTERED |
| enabled: true → false | Перевод в DISABLED, остановка обработки |
| enabled: false → true | Перевод в ACTIVE, возобновление обработки |
| Изменение condition.* | Применение к следующей обрабатываемой свече |

### 10.3 Правила

- Стратегия с `enabled: false` не получает данные, не создаёт Qualified Events.
- Отключение стратегии не удаляет её события из Storage Service.
- При включении стратегия начинает работу со следующей закрытой свечи.

## 11. Требования к производительности

### 11.1 Объём данных (MVP)

- До **250 инструментов** одновременно (CORE_SPECIFICATION.md).
- Таймфрейм **M15** — максимум 250 событий за 15 минут.
- Пиковая нагрузка: ~1 событие в 3.6 секунды (все свечи закрываются одновременно).
- Стратегий в MVP: **1** (LW-001), в будущем — десятки.

### 11.2 Временные ограничения

- Обработка одной свечи одной стратегией: **< 100 мс** (рекомендуется).
- Общее время от закрытия свечи до передачи в Scoring Engine: **< 1 секунда**.
- Уведомление должно уйти за **10 минут** после закрытия свечи (CORE_SPECIFICATION.md) — Strategy Engine не является узким местом.

### 11.3 Масштабируемость

- Стратегии обрабатываются **параллельно** (независимы друг от друга).
- Strategy Engine не должен последовательно дожидаться каждой стратегии — использует fan-out паттерн.
- Количество стратегий не линейно влияет на задержку (параллельная обработка).

### 11.4 Память

- Strategy Engine не накапливает историю свечей (кроме минимального буфера для определения закрытия).
- История для расчёта Liquidation Reference Value хранится в Data Provider или запрашивается при необходимости.
- Состояние стратегий минимально (только конфигурация и текущий статус).

## 12. Масштабирование на десятки стратегий

### 12.1 Архитектурные принципы

| Принцип | Реализация |
|---------|------------|
| **Изоляция** | Стратегии не знают друг о друге, не делят состояние. |
| **Параллелизм** | Обработка стратегий fan-out, без последовательного ожидания. |
| **Конфигурируемость** | Каждая стратегия настраивается через свой блок конфигурации. |
| **Версионирование** | Strategy Engine проверяет версию интерфейса стратегии. |
| **Наблюдаемость** | Каждая стратегия логирует свои метрики независимо. |

### 12.2 Ограничения

- Strategy Engine не ограничивает количество стратегий жёстко.
- Практический предел определяется доступными ресурсами CPU/памяти.
- При 10+ стратегиях рекомендуется параллельная обработка с пулом воркеров.
- При 50+ стратегиях может потребоваться приоритизация (раздел Future Extensions).

## 13. Future Extensions

### 13.1 Зависимые стратегии

Стратегии, которые срабатывают только если сработала другая стратегия.

**Пример:** Стратегия подтверждения тренда должна сработать раньше стратегии входа.

**Реализация:**
- В конфигурации стратегии указывается `depends_on: [Strategy ID]`.
- Strategy Engine проверяет зависимости перед вызовом стратегии.
- Если зависимость не выполнена — стратегия пропускается для данной свечи.

### 13.2 Составные стратегии

Стратегии, объединяющие условия нескольких простых стратегий.

**Пример:** «LW-001 ИЛИ Momentum-001» — срабатывает если сработала хотя бы одна.

**Реализация:**
- Новый тип стратегии: `type: composite`.
- Поле `components: [Strategy ID]` — список под-стратегий.
- Логика комбинации: `AND`, `OR`, `WEIGHTED`.
- Результат — агрегированные метрики.

### 13.3 Стратегии на нескольких таймфреймах

Стратегии, анализирующие данные с разных таймфреймов (M5, M15, H1, H4).

**Реализация:**
- Strategy Engine подписывается на данные нескольких таймфреймов от Data Provider.
- Стратегия объявляет требуемые таймфреймы в конфигурации: `required_timeframes: [M15, H1]`.
- Strategy Engine синхронизирует данные по времени и передаёт стратегии полный набор.
- Вызов стратегии происходит только когда закрылись свечи **на всех** требуемых таймфреймах.

### 13.4 Стратегии с несколькими источниками данных

Стратегии, использующие данные не только от Data Provider, но и внешние источники (ончейн, новости, корреляции).

**Реализация:**
- Strategy Engine предоставляет стратегии доступ к registry внешних провайдеров.
- Стратегия объявляет требуемые источники: `data_sources: [market, onchain, news]`.
- Configuration Manager настраивает подключения к внешним источникам.
- Strategy Engine агрегирует данные и передаёт стратегии единый контекст.

### A.2 Найденные риски

| Риск | Описание | Степень |
|------|----------|---------|
| **Fan-out latency** | При 50+ стратегиях параллельный вызов может создать пиковую нагрузку на CPU. Требуется пул воркеров с ограничением concurrency. | Средняя |
| **Stateful стратегии** | Если стратегия требует истории (например, среднее за 12 свечей), она должна получать её от Data Provider или Storage Service. Не специфицирован механизм запроса истории. | Средняя |
| **Синхронизация многократных вызовов** | Если несколько стратегий подтвердили одну свечу, создаются несколько Qualified Events. Scoring Engine должен корректно обрабатывать множественные оценки одного Market Event. | Низкая |
| **Hot-reload race condition** | При изменении конфигурации в процессе обработки свечи старая стратегия может завершить работу после загрузки новой. Нужен graceful transition. | Низкая |
| **Timeout стратегии** | Долго работающая стратегия может заблокировать обработку свечи. Необходим строгий timeout на уровне Strategy Engine. | Высокая |

### A.3 Предложения по улучшению

| Улучшение | Обоснование |
|-----------|-------------|
| **Приоритизация стратегий** | Добавить поле `priority` в конфигурацию. Высокоприоритетные стратегии обрабатываются первыми, их Qualified Events отправляются в Scoring Engine раньше. |
| **Метаданные стратегий** | Хранить в реестре: описание, автор, дата создания, версия, статус валидации. Упростит управление десятками стратегий. |
| **Dry-run режим** | Возможность запуска стратегии в режиме симуляции без создания Qualified Events (только логирование). Для тестирования новых стратегий на продакшн-данных. |
| **Агрегация метрик** | Strategy Engine собирает статистику по каждой стратегии: количество сработок, среднее время обработки, ошибки. Для мониторинга. |

### A.4 Уровень уверенности

**Высокий.** Документ полностью основан на утверждённой архитектуре (EVENT_ENGINE.md, SYSTEM_ARCHITECTURE.md, CONFIGURATION_SYSTEM.md, DATA_PROVIDER_ARCHITECTURE.md). Все ключевые решения имеют явные источники в спецификациях. Основной риск — таймауты стратегий, но он адресуется через требование строгого timeout на уровне Strategy Engine.
