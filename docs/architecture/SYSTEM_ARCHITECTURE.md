# EVRECONSE System Architecture

**Document Version:** 1.0
**Status:** Draft
**Date:** 2026-07-25

---

## 1. System Overview

EVRECONSE — автоматизированная система идентификации и оценки разворотных свечных паттернов на криптовалютном рынке.

Система не принимает торговых решений. Её задача — анализировать рыночные данные, выявлять паттерны, оценивать их качество и уведомлять пользователя.

Область ответственности системы:

- сбор рыночных данных;
- идентификация торговых паттернов;
- оценка качества паттернов;
- уведомление пользователя;
- логирование событий;
- отслеживание результатов сделок.

## 2. Основные модули системы

| № | Модуль | Назначение |
|---|--------|------------|
| 1 | Data Provider | Получение рыночных данных |
| 2 | Pattern Detector | Идентификация паттернов по стратегии |
| 3 | Scoring Engine | Оценка качества событий |
| 4 | Signal Engine | Принятие решения об уведомлении |
| 5 | Notification Service | Отправка уведомлений пользователю |
| 6 | Outcome Tracker | Отслеживание результатов сделок |
| 7 | Storage Service | Сохранение данных |
| 8 | Configuration Manager | Управление настройками системы |

## 3. Описание модулей

### 3.1 Data Provider

**Назначение:** Получение рыночных данных с биржи в реальном времени.

**Входные данные:**

- конфигурация подключения (биржа, инструменты, таймфрейм);
- список инструментов для отслеживания.

**Выходные данные:**

- сырые рыночные данные (свечи M15, данные о ликвидациях).

**Ответственность:**

- подключение к бирже по WebSocket API;
- поддержание постоянного соединения;
- передача данных в Pattern Detector;
- масштабирование на несколько инструментов.

**НЕ делает:**

- не анализирует данные;
- не принимает решений;
- не хранит данные.

---

### 3.2 Pattern Detector

**Назначение:** Идентификация торговых паттернов на основе правил стратегии.

**Входные данные:**

- рыночные данные от Data Provider;
- параметры стратегии из Configuration Manager.

**Выходные данные:**

- Market Event — каждая закрытая M15 свеча;
- Qualified Event — Market Event, соответствующий условиям стратегии.

**Ответственность:**

- проверка условий входа по стратегии (LW-001 и др.);
- вычисление метрик паттерна (Lower Wick, Body, Wick/Body Ratio);
- передача Qualified Event в Scoring Engine.

**НЕ делает:**

- не оценивает качество сигнала;
- не отправляет уведомления;
- не принимает торговых решений.

---

### 3.3 Scoring Engine

**Назначение:** Количественная оценка качества Qualified Event.

**Входные данные:**

- Qualified Event от Pattern Detector;
- параметры оценки из Configuration Manager.

**Выходные данные:**

- Confidence Score (число от 0 до 100);
- Score Breakdown (детализация по параметрам).

**Ответственность:**

- расчёт оценки по каждому параметру (Lower Wick Quality, Liquidation Strength, Candle Confirmation);
- обеспечение объяснимости оценки (Explainability);
- применение штрафов и бонусов;
- передача результата в Signal Engine.

**Параметры оценки (MVP):**

- Lower Wick Quality;
- Liquidation Strength;
- Candle Confirmation.

**НЕ делает:**

- не принимает решение об уведомлении;
- не изменяет пороговых значений;
- не генерирует сигналов.

---

### 3.4 Signal Engine

**Назначение:** Принятие решения об уведомлении пользователя.

**Входные данные:**

- Confidence Score от Scoring Engine;
- пороговое значение Score из Configuration Manager (по умолчанию 80).

**Выходные данные:**

- Signal — уведомление, если Score >= Threshold.

**Ответственность:**

- сравнение Score с пороговым значением;
- формирование Signal;
- передача Signal в Notification Service и Storage Service.

**НЕ делает:**

- не рассчитывает Score;
- не изменяет порог;
- не отправляет уведомления напрямую.

---

### 3.5 Notification Service

**Назначение:** Отправка уведомлений пользователю.

**Входные данные:**

- Signal от Signal Engine.

**Выходные данные:**

- уведомление в Telegram.

**Содержание уведомления:**

- Symbol
- Exchange
- Timeframe
- Close Price
- Lower Wick %
- Body %
- Wick/Body Ratio
- Liquidation Volume
- Liquidation Reference Value
- Confidence Score
- Event Time (UTC)
- Event ID

**Ответственность:**

- форматирование сообщения;
- отправка через Telegram;
- обработка ошибок отправки.

**НЕ делает:**

- не генерирует сигналы;
- не принимает решений;
- не хранит данные.

---

### 3.6 Outcome Tracker

**Назначение:** Отслеживание результатов сделок после Signal.

**Входные данные:**

- Signal от Signal Engine;
- рыночные данные от Data Provider (для отслеживания TP/SL).

**Выходные данные:**

- Outcome — результат сделки (TP достигнут / SL достигнут / ещё открыта).

**Ответственность:**

- мониторинг цены после Signal;
- фиксация достижения TP (+3%) или SL (-3%);
- логирование результата с указанием фактического профита/убытка.

**НЕ делает:**

- не управляет позициями;
- не исполняет сделки;
- не изменяет TP/SL.

---

### 3.7 Storage Service

**Назначение:** Сохранение всех событий системы.

**Входные данные:**

- Market Events (все, вне зависимости от Score);
- Signals;
- Outcomes.

**Выходные данные:**

- сохранённые данные для последующего анализа.

**Ответственность:**

-persistence всех событий;
- обеспечение целостности данных;
- предоставление данных для анализа.

**НЕ делает:**

- не анализирует данные;
- не принимает решений;
- не удаляет данные без необходимости.

---

### 3.8 Configuration Manager

**Назначение:** Централизованное управление настройками системы.

**Входные данные:**

- конфигурационные файлы;
- переменные окружения.

**Выходные данные:**

- параметры для всех модулей системы.

**Ответственность:**

- предоставление настроек всем модулям;
- валидация конфигурации;
- поддержка изменений без перезапуска (где применимо).

**Настраиваемые параметры (MVP):**

- список инструментов (Top-20 до Top-250);
- порог Score для сигнала;
- TP/SL проценты;
- параметры стратегии;
- API ключи биржи;
- Telegram токен и chat ID.

**НЕ делает:**

- не содержит бизнес-логики;
- не принимает решений;
- не изменяет себя динамически.

## 5. Правила взаимодействия модулей

1. **Data Provider** передаёт данные только в **Pattern Detector**. Никакой другой модуль не получает сырые данные напрямую.

2. **Pattern Detector** передаёт **Qualified Event** в **Scoring Engine**. Все Market Events также передаются в **Storage Service**.

3. **Scoring Engine** передаёт **Score** в **Signal Engine**. Он не взаимодействует напрямую с Notification Service или Storage Service.

4. **Signal Engine** принимает решение и передаёт **Signal** в **Notification Service** и **Storage Service**.

5. **Outcome Tracker** получает Signal от Signal Engine и данные от Data Provider. Результат передаёт в Storage Service.

6. **Configuration Manager** — единственный источник конфигурации. Модули не имеют собственных настроек.

7. **Storage Service** — пассивный модуль. Он только сохраняет данные, но не инициирует взаимодействие.

8. Модули общаются последовательно. Каждый модуль завершает свою работу до передачи данных следующему.

9. Ошибка в одном модуле не должна блокировать работу других модулей.

## 6. Архитектурные принципы

### Single Responsibility

Каждый модуль отвечает ровно за одну функцию системы. Разделение ответственности явное: сбор данных, обнаружение паттернов, оценка, принятие решения, уведомление, хранение.

### Loose Coupling

Модули взаимодействуют через чётко определённые входные и выходные данные. Ни один модуль не знает о внутренней реализации другого. Замена модуля не требует изменений в других модулях при сохранении формата данных.

### High Cohesion

Внутри каждого модуля все элементы связаны одной целью. Pattern Detector работает только с паттернами, Scoring Engine — только с оценкой. Нет пересечения ответственности.

### Documentation First

Архитектура документирована до начала реализации. Изменения вносятся сначала в документацию, затем в код.

### Configuration First

Все параметры, которые могут измениться, вынесены в конфигурацию. В коде нет зашитых значений (No Magic Numbers).

## 7. Расширяемость без изменения ядра

### Добавление стратегий

Новая стратегия добавляется как новый модуль Pattern Detector (или расширение существующего). Ядро системы (Scoring Engine, Signal Engine, Notification Service) не изменяется. Стратегия подключается через Configuration Manager.

### Добавление бирж

Новый Data Provider реализуется для каждой биржи. Выходной формат данных остаётся единым для всех бирж. Остальные модули не изменяются.

### Добавление способов уведомлений

Новый Notification Service добавляется как дополнительный канал. Signal Engine передаёт Signal всем зарегистрированным сервисам уведомлений без изменения своей логики.

### Добавление параметров оценки

Новый параметр Scoring добавляется как модуль в Scoring Engine. Существующие параметры не изменяются. Score пересчитывается с учётом всех активных параметров. Параметр включается/отключается через конфигурацию.

## 8. Нефункциональные требования

### Надёжность

- Система должна работать без сбоев не менее 7 дней подряд.
- При потере соединения с биржей Data Provider должен автоматически переподключаться.
- При недоступности Telegram Notification Service не должен терять сигналы.
- Ошибки в одном модуле не должны останавливать систему.

### Расширяемость

- Добавление новой стратегии не требует изменения существующих модулей.
- Добавление новой биржи не требует изменения ядра.
- Добавление нового канала уведомлений изолировано в одном модуле.

### Сопровождаемость

- Configuration First — все настройки в конфигурационных файлах.
- Documentation First — архитектура документирована.
- Explainability — каждый Score имеет детализацию по параметрам.
- Логирование всех событий для диагностики.

### Тестируемость

- Каждый модуль тестируется изолированно.
- Входные и выходные данные модулей чётко определены.
- Зависимости модулей явные (через входные данные).
- Модули не имеют скрытых состояний.

### Производительность

- Система обрабатывает до 250 инструментов с таймфреймом M15.
- Уведомление должно быть отправлено в течение 10 минут после закрытия свечи.
- Объём данных: все Market Events (вне зависимости от Score), Signals, Outcomes.
