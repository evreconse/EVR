# EVRECONSE Event Engine Specification

**Document Version:** 1.0
**Status:** Draft
**Date:** 2026-07-25

---

## 1. Что такое Market Event

**Market Event** — базовое событие системы, которое создаётся при закрытии каждой M15 свечи по каждому отслеживаемому инструменту.

Событие — это единица информации, которая проходит через всю систему. Каждое событие имеет уникальный идентификатор, статус и набор данных.

Типы событий:

| Тип | Описание |
|-----|----------|
| Market Event | Событие о закрытии свечи. Создаётся всегда для каждого инструмента. |
| Qualified Event | Market Event, прошедший проверку условий стратегии. |
| Signal | Qualified Event с Confidence Score, достигшим порога уведомления. |
| Outcome | Signal, по которому завершено отслеживание TP/SL. |

---

## 2. Полный жизненный цикл события

### 2.1 Создание (NEW)

При закрытии M15 свечи Strategy Engine создаёт **Market Event** с начальными рыночными данными.

### 2.2 Проверка стратегией (QUALIFIED)

Strategy Engine передаёт Market Event каждой зарегистрированной стратегии. Если стратегия находит паттерн, событие переходит в статус **QUALIFIED** и дополняется метриками паттерна.

Если ни одна стратегия не подтвердила событие, оно сохраняется как Market Event в статусе **NEW** и завершает жизненный цикл.

### 2.3 Оценка (SCORED)

Qualified Event передаётся в Scoring Engine. Scoring Engine рассчитывает Confidence Score и Score Breakdown. Событие переходит в статус **SCORED**.

### 2.4 Принятие решения (SIGNAL / DISMISSED)

Scored Event передаётся в Notification Service. Notification Service сравнивает Score с порогом из конфигурации.

- Если Score >= порога → событие переходит в статус **SIGNAL**, отправляется уведомление.
- Если Score < порога → событие переходит в статус **DISMISSED**, уведомление не отправляется.

### 2.5 Отслеживание (MONITORING)

Signal передаётся в Outcome Tracker. Outcome Tracker начинает мониторинг цены инструмента. Событие переходит в статус **MONITORING**.

### 2.6 Завершение (COMPLETED / EXPIRED)

При достижении TP (+3%) или SL (-3%) Outcome Tracker фиксирует результат. Событие переходит в статус **COMPLETED**.

Если событие не было подтверждено ни одной стратегией или не достигло порога Score, оно завершается в статусе **DISMISSED** или остаётся как **NEW**.

## 3. Статусы события

```
         ┌──────────┐
         │   NEW    │  ← Создано при закрытии свечи
         └────┬─────┘
              │
     ┌────────┴────────┐
     ▼                 ▼
┌──────────┐    (сохраняется
│ QUALIFIED│     как NEW)
└────┬─────┘
     │
     ▼
┌──────────┐
│  SCORED  │  ← Оценено Scoring Engine
└────┬─────┘
     │
     ┌──────┴──────┐
     ▼             ▼
┌──────────┐ ┌──────────┐
│  SIGNAL  │ │DISMISSED │  ← Score < порога
└────┬─────┘ └──────────┘
     │
     ▼
┌──────────┐
│MONITORING│  ← Отслеживание TP/SL
└────┬─────┘
     │
     ┌──────┴──────┐
     ▼             ▼
┌──────────┐ ┌──────────┐
│COMPLETED │ │ EXPIRED  │  ← TP/SL не достигнуты за лимит
└──────────┘ └──────────┘
```

| Статус | Описание |
|--------|----------|
| **NEW** | Событие создано, ожидает проверки стратегиями. |
| **QUALIFIED** | Условия хотя бы одной стратегии выполнены. |
| **SCORED** | Confidence Score рассчитан. |
| **SIGNAL** | Score достиг порога, уведомление отправлено. |
| **DISMISSED** | Score ниже порога, уведомление не отправлено. |
| **MONITORING** | Отслеживается достижение TP/SL. |
| **COMPLETED** | TP или SL достигнут, результат зафиксирован. |
| **EXPIRED** | Событие устарело (например, превышено время ожидания TP/SL). |

## 4. Какие данные хранит событие

### Всегда

| Поле | Тип | Описание |
|------|-----|----------|
| Event ID | Уникальный идентификатор | UUID события |
| Status | Статус | Текущий статус |
| Symbol | Строка | Тикер инструмента (BTCUSDT) |
| Exchange | Строка | Биржа (Bybit) |
| Timeframe | Строка | Таймфрейм (M15) |
| Event Time | UTC timestamp | Время закрытия свечи |
| Created At | UTC timestamp | Время создания события |
| Updated At | UTC timestamp | Время последнего изменения |

### На этапе NEW

| Поле | Описание |
|------|----------|
| Open, High, Low, Close | Цены свечи |
| Volume | Объём торгов |

### На этапе QUALIFIED

| Поле | Описание |
|------|----------|
| Strategy ID | Идентификатор стратегии (LW-001) |
| Lower Wick | Размер нижней тени |
| Body | Размер тела свечи |
| Wick/Body Ratio | Отношение тени к телу |
| Liquidation Volume | Объём ликвидаций |
| Liquidation Reference Value | Референтное значение ликвидаций |
| Lower Wick % | Процент нижней тени |

### На этапе SCORED

| Поле | Описание |
|------|----------|
| Confidence Score | Итоговая оценка (0-100) |
| Score Breakdown | Детализация по параметрам |

### На этапе SIGNAL

| Поле | Описание |
|------|----------|
| Notification Timestamp | Время отправки уведомления |
| Close Price | Цена закрытия на момент сигнала |

### На этапе MONITORING / COMPLETED

| Поле | Описание |
|------|----------|
| Outcome | TP достигнут / SL достигнут |
| Actual Profit % | Фактический профит или убыток |
| Outcome Timestamp | Время завершения |

## 5. Кто может создавать события

| Модуль | Тип события | Условие |
|--------|-------------|---------|
| **Strategy Engine** | Market Event | Каждая закрытая M15 свеча |
| **Strategy Engine** | Qualified Event | Market Event, прошедший условия стратегии |
| **Notification Service** | Signal | Scored Event с Score >= порога |
| **Notification Service** | Dismissed Event | Scored Event с Score < порога |
| **Outcome Tracker** | Outcome | Signal, достигший TP/SL |

Только эти модули имеют право создавать события. Никакой другой модуль не может инициировать новое событие.

---

## 6. Кто может изменять события

| Модуль | Что изменяет |
|--------|--------------|
| **Strategy Engine** | Статус: NEW → QUALIFIED. Добавляет метрики паттерна. |
| **Scoring Engine** | Статус: QUALIFIED → SCORED. Добавляет Score и Breakdown. |
| **Notification Service** | Статус: SCORED → SIGNAL или DISMISSED. |
| **Outcome Tracker** | Статус: SIGNAL → MONITORING → COMPLETED. Добавляет Outcome. |
| **Storage Service** | Не изменяет события. Только сохраняет. |

Событие не может быть изменено модулем, который не участвует в его жизненном цикле.

---

## 7. Кто имеет право только читать события

| Модуль | Что читает | Для чего |
|--------|------------|----------|
| **Configuration Manager** | Не читает события | Работает только с конфигурацией. |
| **Storage Service** | Все события | Для сохранения и последующего предоставления данных. |
| **Outcome Tracker** | Signal | Для начала мониторинга цены. |
| **Notification Service** | Scored Event | Для проверки порога и отправки. |

Storage Service имеет доступ на чтение ко всем событиям, но не может их изменять.

---

## 8. Правила передачи события между модулями

1. **Событие передаётся строго по цепочке:** Strategy Engine → Scoring Engine → Notification Service → Outcome Tracker.

2. **Каждый модуль получает событие, только когда предыдущий модуль завершил обработку.**

3. **Событие не может быть пропущено.** Нельзя отправить событие напрямую из Strategy Engine в Notification Service, минуя Scoring Engine.

4. **Событие не может быть передано более чем одному модулю одновременно** (за исключением Storage Service, который получает копию асинхронно).

5. **Storage Service получает копию каждого события** на каждом этапе жизненного цикла для сохранения.

6. **Если модуль не может обработать событие** (ошибка, недоступность), событие не теряется. Модуль должен повторить попытку или сохранить событие для последующей обработки.

7. **Формат события един для всей системы.** Все модули работают с одинаковой структурой события. Добавление новых полей не должно ломать существующие модули.

---

## 9. Что запрещено делать с событиями

1. **Запрещено изменять событие после его завершения.** Событие в статусе COMPLETED или DISMISSED не подлежит изменениям.

2. **Запрещено удалять события.** Все события должны сохраняться для анализа.

3. **Запрещено создавать события в обход Strategy Engine.** Никакой другой модуль не может инициировать новый Market Event.

4. **Запрещено изменять статус события назад.** Статусы изменяются только вперёд по жизненному циклу.

5. **Запрещено передавать событие нескольким экземплярам одного модуля.** Каждое событие обрабатывается ровно один раз каждым модулем.

6. **Запрещено хранить состояние в событии, не предусмотренное его типом.** Нельзя добавлять поля, не описанные в спецификации события.

7. **Запрещено пропускать этапы жизненного цикла.** Событие не может перейти из NEW сразу в SIGNAL.

## 10. Возможности расширения в будущем

### 10.1 Приоритеты событий

События от разных стратегий могут иметь разные приоритеты. Высокоприоритетные события обрабатываются вне очереди.

### 10.2 Пакетная обработка

При большом количестве инструментов события могут обрабатываться не по одному, а пачками (batch) для повышения производительности.

### 10.3 Группировка событий

Несколько событий по одному инструменту от разных стратегий могут быть сгруппированы в одно уведомление.

### 10.4 Каскадные события

Одно событие может порождать дочерние события (например, Signal порождает Outcome). Отслеживание родительских связей.

### 10.5 События по расписанию

Плановые события, не привязанные к закрытию свечи (например, ежедневная статистика, уведомления о состоянии системы).

### 10.6 Системные события

События, связанные не с рынком, а с состоянием системы (ошибки подключения, перезапуски, изменения конфигурации).

## Приложение A: Предложенные архитектурные улучшения

На основе анализа SYSTEM_ARCHITECTURE.md вносятся следующие изменения:

### Улучшение 1: Упразднение Signal Engine

**Текущая архитектура:** Signal Engine — отдельный модуль, который сравнивает Score с порогом и формирует Signal. Notification Service только отправляет сообщение.

**Проблема:** Signal Engine выполняет единственную операцию — сравнение числа с порогом. Это недостаточная ответственность для выделенного модуля. Граница между «принять решение об уведомлении» и «отправить уведомление» искусственна.

**Решение:** Устранить Signal Engine как отдельный модуль. Передать его ответственность Notification Service.

**Новая ответственность Notification Service:**

- получение Scored Event от Scoring Engine;
- сравнение Confidence Score с порогом из Configuration Manager;
- если Score >= порога — перевод события в статус SIGNAL и отправка уведомления;
- если Score < порога — перевод события в статус DISMISSED.

**Преимущества:**

- уменьшение количества модулей без потери функциональности;
- устранение лишней передачи данных между модулями;
- Notification Service становится полновластным владельцем решения об уведомлении;
- упрощение цепочки передачи: Scoring Engine → Notification Service → Outcome Tracker.

### Улучшение 2: Замена Pattern Detector на Strategy Engine

**Текущая архитектура:** Pattern Detector — модуль, проверяющий условия одной стратегии.

**Проблема:** Для поддержки нескольких стратегий потребуется либо несколько Pattern Detector, либо внесение логики маршрутизации в существующий модуль, что нарушает Single Responsibility.

**Решение:** Заменить Pattern Detector на Strategy Engine.

**Strategy Engine:**

- получает рыночные данные от Data Provider;
- управляет набором зарегистрированных стратегий;
- передаёт каждую закрытую свечу всем активным стратегиям;
- собирает результаты от всех стратегий;
- создаёт Market Event для каждой свечи;
- создаёт Qualified Event для каждой стратегии, подтвердившей паттерн;
- передаёт Qualified Events в Scoring Engine.

**Каждая стратегия — изолированный модуль:**

- получает сырые рыночные данные;
- проверяет свои условия;
- возвращает результат (подтверждено / не подтверждено) с метриками.

Стратегия не имеет доступа к другим стратегиям, Scoring Engine или Notification Service.

**Преимущества:**

- поддержка нескольких стратегий без изменения ядра;
- стратегии изолированы друг от друга;
- добавление новой стратегии = добавление модуля + регистрация в Strategy Engine;
- Strategy Engine берёт на себя маршрутизацию, а не распознавание паттернов.
