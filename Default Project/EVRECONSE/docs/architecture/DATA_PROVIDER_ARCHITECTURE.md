# DATA_PROVIDER_ARCHITECTURE.md

# EVRECONSE Data Provider Architecture

**Document Version:** 1.0
**Status:** Draft
**Date:** 2026-07-25

---

## 1. Назначение Data Provider

Data Provider — модуль системы, отвечающий за получение рыночных данных с биржи в реальном времени.

Он является единственным источником внешних данных для всей системы. Никакой другой модуль не подключается к бирже напрямую.

Data Provider не анализирует данные, не принимает решений и не хранит данные. Его задача — доставить сырые рыночные данные от биржи до внутренних модулей системы в максимально сыром, необработанном виде.

---

## 2. Ответственность модуля

- подключение к бирже по WebSocket API;
- поддержание постоянного соединения (keep-alive);
- получение данных по всем отслеживаемым инструментам;
- передача полученных данных в Strategy Engine;
- передача ценовых данных в Outcome Tracker (для мониторинга TP/SL);
- валидация входящих данных перед передачей;
- обработка ошибок соединения и данных;
- автоматическое переподключение при потере соединения;
- синхронизация времени;
- масштабирование на несколько инструментов (от 20 до 250).

---

## 3. Типы рыночных данных

На основе утверждённой документации система получает следующие типы данных:

### 3.1 Свечи (Candles / OHLCV)

Данные о закрытых M15 свечах для каждого отслеживаемого инструмента.

Каждая свеча содержит:
- время закрытия (UTC);
- цена открытия (Open);
- максимальная цена (High);
- минимальная цена (Low);
- цена закрытия (Close);
- объём торгов (Volume).

**Источник требования:** CORE_SPECIFICATION.md, MARKET_EVENT_SCHEMA.md.

**Примечание:** Documentation указывает, что стратегия работает только с полностью сформированными (закрытыми) свечами. Data Provider должен предоставлять именно закрытые свечи, а не потоковые данные незавершённых свечей.

### 3.2 Данные о ликвидациях (Liquidation Data)

Данные о ликвидациях, происходящих на бирже.

Формат и состав данных о ликвидациях в документации не детализированы. Известно, что для LW-001 необходим объём ликвидаций (Liquidation Volume) и референтное значение (Liquidation Reference Value), рассчитываемое как среднее за последние 12 свечей.

**Источник требования:** LW-001.md.

**Недостаток информации:** Документация не уточняет:
- что именно представляет собой Liquidation Volume (сумма ликвидаций за свечу, количество, в USD или в контрактах);
- как часто поступают данные о ликвидациях (real-time stream или агрегированные за интервал);
- требуется ли различие между long и short ликвидациями.

### 3.3 Данные для Outcome Tracker

Ценовые данные в реальном времени, необходимые для отслеживания достижения TP/SL после отправки Signal.

Outcome Tracker получает данные от Data Provider напрямую. Тип данных — цена закрытия свечи (Close) или текущая рыночная цена для мониторинга уровня TP и SL.

**Источник требования:** SYSTEM_ARCHITECTURE.md.

**Недостаток информации:** Документация не уточняет:
- с какой частотой Outcome Tracker получает данные (каждая новая свеча, stream тиков);
- достаточно ли данных M15 или требуется более высокая частота.

## 4. Данные, необходимые для LW-001

На основе LW-001.md стратегия использует следующие рыночные данные:

| Данные | Для чего | Источник |
|--------|----------|----------|
| Open, High, Low, Close | Расчёт Lower Wick, Body, Wick/Body Ratio, Lower Wick %, Body % | Свеча M15 |
| Volume | Игнорируется стратегией, но сохраняется | Свеча M15 |
| Liquidation Volume | Условие 4 — свеча сопровождается ростом ликвидаций | Данные о ликвидациях |
| Liquidation Reference Value | Среднее значение ликвидаций за последние 12 свечей | История ликвидаций |

LW-001 требует историю данных (минимум 12 свечей) для расчёта Liquidation Reference Value. Data Provider должен обеспечить возможность получения исторических данных при запуске или накопления их в течение работы.

## 5. Поток данных до Strategy Engine

```
Биржа (WebSocket API)
        │
        │  Сырые данные
        ▼
  ┌─────────────────┐
  │  Data Provider  │
  │                  │
  │  1. Получение    │
  │  2. Валидация    │
  │  3. Нормализация │
  └──────┬──────────┘
         │
         ├────────────────────────────────────┐
         │  Закрытые свечи M15 + ликвидации    │  Ценовые данные (мониторинг)
         ▼                                    ▼
  ┌─────────────────┐              ┌──────────────────┐
  │ Strategy Engine │              │ Outcome Tracker  │
  └─────────────────┘              └──────────────────┘
```

Data Provider — единственный модуль, который подключается к внешнему источнику. Он передаёт данные в два модуля:

1. **Strategy Engine** — получает закрытые свечи и данные о ликвидациях для анализа паттернов.
2. **Outcome Tracker** — получает ценовые данные для отслеживания TP/SL.

## 6. Правила валидации входящих данных

Data Provider должен проверять следующие аспекты перед передачей данных в Strategy Engine:

### 6.1 Проверка полноты данных

- Свеча должна содержать все значения OHLCV.
- Время закрытия свечи должно быть заполнено.
- Данные о ликвидациях должны содержать значение объёма.

Если данные неполные — они отбрасываются. Неполные данные не передаются дальше.

### 6.2 Проверка корректности значений

- Open, High, Low, Close должны быть положительными числами.
- High >= Max(Open, Close).
- Low <= Min(Open, Close).
- Volume >= 0.
- Время закрытия свечи должно быть в разумных пределах (не в будущем, не старше допустимого порога).

Если значения некорректны — свеча отбрасывается.

### 6.3 Проверка последовательности

- Свечи должны поступать в хронологическом порядке.
- Пропуск свечи должен быть зафиксирован и залогирован.
- При обнаружении пропуска Data Provider не должен пытаться восстановить пропущенную свечу самостоятельно.

### 6.4 Проверка дубликатов

- Если получена свеча с временем закрытия, уже переданным ранее, — она отбрасывается как дубликат.

### 6.5 Проверка принадлежности инструмента

- Данные принимаются только по инструментам, указанным в конфигурации.
- Данные по инструментам вне списка игнорируются.

## 7. Обработка ошибок

### 7.1 Ошибки данных

| Ситуация | Действие |
|----------|----------|
| Некорректная свеча (OHLCV) | Отбросить, залогировать |
| Дубликат свечи | Отбросить, залогировать |
| Нарушение последовательности свечей | Залогировать, продолжить со следующей |
| Некорректные данные о ликвидациях | Отбросить только эту запись, не прерывать поток |
| Пустой ответ от биржи | Игнорировать, ожидать следующее сообщение |

### 7.2 Ошибки соединения

| Ситуация | Действие |
|----------|----------|
| Разрыв WebSocket соединения | Инициировать переподключение |
| Таймаут соединения | Инициировать переподключение |
| Ошибка аутентификации | Залогировать, остановить работу модуля |
| Превышение лимита запросов (rate limit) | Пауза перед следующим запросом |

### 7.3 Принципы обработки ошибок

- Ни одна ошибка Data Provider не должна останавливать систему в целом.
- Ошибки логируются для последующей диагностики.
- При невозможности получить данные по одному инструменту, Data Provider продолжает получать данные по остальным инструментам.
- При недоступности биржи Data Provider не должен пытаться получить данные из другого источника.

## 8. Переподключение после потери соединения

Требование из SYSTEM_ARCHITECTURE.md: «При потере соединения с биржей Data Provider должен автоматически переподключаться».

### Правила переподключения

1. При разрыве соединения Data Provider немедленно инициирует переподключение.
2. Первая попытка переподключения выполняется без задержки.
3. При неудаче каждой последующей попытки задержка увеличивается (exponential backoff).
4. Максимальная задержка между попытками не должна превышать 5 минут.
5. Количество попыток не ограничено — Data Provider должен пытаться переподключиться до успеха или до остановки системы.
6. После успешного переподключения Data Provider должен запросить недостающие данные за время отсутствия, если это поддерживается биржей.
7. Если получение пропущенных данных невозможно — Data Provider продолжает работу с текущего момента.

### Состояние при переподключении

- Data Provider не хранит состояние между подключениями.
- После переподключения Data Provider начинает получать данные с текущего момента.
- Все инструменты из конфигурации подписываются заново.

---

## 9. Правила синхронизации времени

Система работает с временем в UTC. Все события маркируются временем закрытия свечи по часам биржи.

### Требования

- Data Provider должен использовать время, полученное от биржи, а не локальное время системы.
- Расхождение между временем биржи и временем Data Provider не должно влиять на маркировку событий.
- Время закрытия свечи (Event Time) — это время, указанное биржей в данных свечи.

### Действия при рассинхронизации

- Если Data Provider обнаруживает, что время его системы существенно расходится со временем биржи (более 5 секунд), он должен залогировать предупреждение.
- Data Provider не должен корректировать время закрытия свечи. Время закрытия берётся из данных биржи как есть.

---

## 10. Требования к производительности

### 10.1 Количество инструментов

Data Provider должен поддерживать от 20 до 250 инструментов одновременно (CORE_SPECIFICATION.md).

### 10.2 Таймфрейм

Единственный таймфрейм для MVP — M15 (15 минут).

Для 250 инструментов это означает максимум 250 событий в 15 минут, или примерно 1 событие в 3,6 секунды в пике (все свечи закрываются одновременно).

### 10.3 Задержка

- Уведомление должно быть отправлено в течение 10 минут после закрытия свечи (CORE_SPECIFICATION.md).
- Data Provider не является узким местом — задержка на уровне сбора данных должна быть минимальной (секунды, не минуты).

### 10.4 Объём данных

Объём данных на один инструмент:
- одна свеча (OHLCV) + одна запись о ликвидациях за 15 минут.

Для 250 инструментов: ~250 свечей за 15 минут.

### 10.5 Непрерывность

Система должна работать без сбоев не менее 7 дней подряд (CORE_SPECIFICATION.md). Data Provider должен поддерживать соединение в течение всего этого периода.

---

## 11. Подключение новых бирж

Требование из SYSTEM_ARCHITECTURE.md: добавление новой биржи не требует изменения ядра системы.

### Принцип

Data Provider — это абстрактный слой. Каждая биржа — отдельная реализация этого слоя.

### Правила

- Все реализации Data Provider имеют единый формат выходных данных.
- Переход на другую биржу не требует изменения Strategy Engine, Scoring Engine, Notification Service, Outcome Tracker, Storage Service.
- Биржа выбирается через конфигурацию (Configuration Manager).
- Data Provider для конкретной биржи отвечает за:
  - особенности подключения (WebSocket, REST);
  - особенности аутентификации;
  - особенности формата данных биржи;
  - нормализацию данных к единому внутреннему формату.

### Что НЕ должен делать Data Provider новой биржи

- Менять формат данных системы.
- Влиять на работу других модулей.
- Добавлять бизнес-логику.

---

## 12. Что Data Provider делать НЕ должен

На основе SYSTEM_ARCHITECTURE.md и принципов архитектуры:

1. **Не анализирует данные.** Data Provider не рассчитывает метрики паттернов, не сравнивает значения, не принимает решений.

2. **Не принимает решений.** Data Provider не решает, какие данные важны, а какие нет (за исключением валидации).

3. **Не хранит данные.** Data Provider не является базой данных. Он передаёт данные дальше, но не хранит их для повторного использования. Исключение — временный буфер для определения закрытия свечи (см. ниже) и история для расчёта Liquidation Reference Value, но эта история должна быть минимальной.

4. **Не создаёт события.** Data Provider не создаёт Market Event. Событие создаёт Strategy Engine.

5. **Не подключается к нескольким биржам одновременно** (в рамках MVP). Каждый экземпляр Data Provider работает с одной биржей.

6. **Не обрабатывает ордера.** Система не исполняет сделки, и Data Provider не имеет функциональности для отправки ордеров.

7. **Не управляет подписками динамически.** Изменение списка инструментов — ответственность Configuration Manager, не Data Provider.

8. **Не кеширует данные для других модулей.** Если модулю нужны исторические данные — он получает их из Storage Service, а не из Data Provider.

### Уточнение по временному буферу

Data Provider может временно хранить данные незавершённой свечи для определения момента её закрытия, но после закрытия и передачи свечи эти данные должны быть освобождены. Data Provider не накапливает историю более чем необходимо для определения границ свечей.

| Вопрос | Статус |
|--------|--------|
| Data Provider передаёт данные в Strategy Engine | ✅ Соответствует EVENT_ENGINE.md |
| Data Provider передаёт данные в Outcome Tracker | ✅ Соответствует SYSTEM_ARCHITECTURE.md |
| Data Provider использует WebSocket | ✅ Соответствует CORE_SPECIFICATION.md |
| Data Provider не создаёт события | ✅ Соответствует EVENT_ENGINE.md |
| Data Provider не хранит данные | ✅ Соответствует SYSTEM_ARCHITECTURE.md |
| Data Provider не зависит от биржи | ✅ Соответствует принципу Loose Coupling |
| Data Provider не принимает решений | ✅ Соответствует SYSTEM_ARCHITECTURE.md |

Противоречий не обнаружено.

### A.2 Риски

| Риск | Описание | Степень |
|------|----------|---------|
| **Неопределённость формата данных о ликвидациях** | Документация не специфицирует, что такое Liquidation Volume — сумма в USD, количество контрактов, количество ликвидаций. Разные биржи предоставляют разные форматы. Реализация может потребовать уточнения. | Высокая |
| **Зависимость от WebSocket** | При нестабильном соединении Data Provider может пропускать свечи. Механизм восстановления пропущенных данных не специфицирован и может отличаться на разных биржах. | Средняя |
| **История для Liquidation Reference Value** | LW-001 требует среднее за 12 свечей. Если система только запущена, история отсутствует. Не специфицировано, откуда брать первые 12 значений. | Средняя |
| **Производительность при 250 инструментах** | 250 одновременных WebSocket подписок могут создать нагрузку на соединение. Не специфицировано, использует ли Data Provider одну подписку на все инструменты или индивидуальные. | Средняя |
| **Outcome Tracker и частота данных** | Outcome Tracker получает данные от Data Provider для мониторинга TP/SL. Не специфицировано, нужны ли ему данные реального времени (тика) или достаточно закрытых свеч M15. | Средняя |
| **Синхронизация времени** | Разные биржи могут маркировать время закрытия свечи по-разному. Расхождение может влиять на корректность определения закрытия свечи. | Низкая |

### A.3 Рекомендуемые улучшения

| Улучшение | Обоснование |
|-----------|-------------|
| **Специфицировать формат Liquidation Volume** | Добавить в документацию точное определение: Liquidation Volume — это совокупный объём ликвидаций в USD за период свечи. |
| **Специфицировать начальную загрузку истории** | Определить, откуда Data Provider получает первые 12 свечей для расчёта Liquidation Reference Value (REST API биржи при запуске). |
| **Разделить поток данных для Outcome Tracker** | Outcome Tracker, вероятно, требует более высокую частоту данных, чем M15. Рекомендуется уточнить в документации — достаточно ли ему данных о закрытии свечи или нужен stream цен. |
| **Добавить heartbeat-механизм** | Data Provider должен периодически проверять состояние соединения (ping/pong) для раннего обнаружения разрыва. |
| **Уточнить стратегию восстановления пропусков** | Если переподключение заняло время и свечи были пропущены, Data Provider должен попытаться получить их через REST API перед переходом в реальный режим. |
